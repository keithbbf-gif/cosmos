## 4. The finding that would have broken the first real push

Walking `V:\Ai` produced **2,091 unreadable files**, every one of them
`FileNotFoundError winerror=3` on paths **282 characters** long — classic Windows

## 6. Verification — what would PROVE a restore works

A green exit code proves nothing; neither does a 200 from a PUT. Three gates, each
bound to a value only a real run can emit.

**Gate A — the push read-back (automatic, every push).** `push()` does not trust the
PUT. After storing, it GETs **every object back** into a scratch directory and re-hashes
it against the sealed manifest. Any drift is `R2_HASH_MISMATCH` and the push refuses.
The receipt's `readback_verified` must equal `files_pushed`.

**Gate B — the cold restore rehearsal.** Restore from the bucket into an *empty* scratch
dir on a *different* volume, re-hash every file, and require the sealed
`manifest_seal_sha256` in the rehearsal artifact to match the manifest stored in the
bucket. This is `cosmos_backup.do_rehearse` pointed at `R2Target` instead of
`LocalDirTarget` — the interface is already shared, which is why the seam was worth
building this way.

**Gate C — the one that actually counts: restore to a machine that is not this one.**
A restore rehearsed only on the machine that wrote it has never tested the failure it
exists for. The proof is `cosmos.py install` + restore-from-R2 on a cold peer (SRV1 or
T7, per the FEDERATION wish), then `cosmos.py audit` returning `"ok": true` on the
restored tree. Until that runs, offsite restorability is **UNMEASURED** — this plan
does not get to claim it.

**What must never count as verification:** a green log, an exit code, a byte count that
matches, or a listing that shows the objects exist. Only a re-hash of restored bytes.

## 7. Design decisions worth naming

**Stdlib SigV4 instead of `rclone`/`boto3`/`aws`.** None of the three is installed
(measured), and adding one adds a dependency that can go stale, break on a Python
upgrade, or need its own credential store — a second place for a key to sit. R2 speaks
the S3 API and SigV4 is `hmac` + `hashlib`: ~40 lines, no dependency, and checkable
against AWS's own published vectors. The signer is a **pure function** with the clock
injected, which is the only reason those vectors can be run through it at all.

**One hash, two jobs.** S3 requires `x-amz-content-sha256` on every signed PUT. The
backup manifest already carries a per-file sha256. They are the same value, so the file
is hashed **once** and that hash serves both the restore proof and the request
signature. A test pins them equal so they cannot drift apart.

**An injected transport, the ITC idiom.** `R2Target` takes a `Transport`. Production
passes `UrllibTransport`; tests and `selfcheck` pass `MemoryTransport`. No test can
open a socket, so a green suite never depends on reachability — and the *entire*
pipeline (sign → PUT → GET → re-hash → seal) is provable with zero credentials. That is
what `selfcheck` is: everything except the wire, proven offline.

**The push refuses secrets rather than encrypting them.** `COVERAGE.md` gap 4:
`config/install_key.bin` (the ledger signing key) is inside the live backup sets, and
`.git/config` carries a plaintext remote credential. Off-machine storage inherits every
exposure in scope, so `SECRETS_IN_SCOPE` refuses the push by **manifest path alone** —
the scan never opens a file. There is deliberately **no override flag**: the remedies
are to exclude them, or to build encryption-at-rest and lift the refusal properly.
An override would become the default within a week.
