# Pack weight follows the door

Keith 2026-09-25. Overlap between a HERO pack and a harness is on purpose.
Harnesses are not equal. A pack lets a strong agent run under a weak door
or under no harness at all. Adapt the pack to the door it is about to run on.
Do not ship one fat pack to every binary. Core stays small; extra
layers are revealed per attempt (`CORE_REVEAL.md`).

## Rule

The door binds what it actually binds. The pack carries the rest.
`require_duds` only checks the outfit. Applied still means that door bound
each layer it claims, and the reply obeyed.

| Door strength | Examples | Pack carries | Pack does not restuff |
|---|---|---|---|
| Strong | COSMOS CODE, Pi, OpenCode, Codex, dsh, grok.exe | Role, model pin, mission, first-line contract | Loop, tool pool, worktree, permission law |
| Weak | OpenRouter chat, Vertex `generateContent` (no tools) | Wrapper, tool policy, first-line, host PathJail write | A fake tools array the API never applied |
| None | Bare mouth, no binary | All eight layers, host-side jail and stop | A claim that a harness ran |

COSMOS CODE is the strong door we are building. Under it the pack goes thin:
pin, mission, oracle when the WO is nontrivial. Jail, hooks, and DoneBundle
stay in the rail, not copied into the prompt.

Under a weak door the same agent needs the fat outfit: `WRAP.md` on the
wire, STYLE off the OpenRouter system turn, write through PathJail by the
caller, grade the worktree or the filed text — not HTTP 200.

## Not

One `LAYERS.md` pasted into every system prompt. AI Mode layer-tracker
scripts. Treating a written sample file as proof the door bound the layers.
