# 1. BLOCKING findings

### B1 — `deck_studio.js` does not parse

- **File:** `builds/cdeck/ui/deck_studio.js`
- **Exact anchor/range:** immediately after:
  ```js
  window.deckOpenResearchCall = window.openStudioResearchCall;
    };
  function bindStudioForms() {
  ```
- **Reason:** the second `};` is unmatched at that point. The enclosing IIFE is later closed again with `})();`. A JavaScript parser will reject the file, preventing `initDeckStudio`, Studio, Runs, and Review from loading.
- **Reproduce:**
  ```text
  node --check builds/cdeck/ui/deck_studio.js
  ```
- **Proposed test:** add a deterministic syntax check for every `builds/cdeck/ui/*.js`, not only string-presence assertions.

### B2 — HTTP Crucible handler is an additional queue claimant and executor

- **File:** `cosmos/cosmos_service.py`
- **Exact branch:** `if self.path == "/api/v1/crucible":`
- **Relevant lines:**
  ```python
  q = kernel.sched.queued()
  if q and q[0]["job_id"] == jid:
      kernel.sched.claim_next()
      claimed = True
  ...
  verdict = cru.run_round(pkt, dispatchers)
  ```
- **Reason:** the binding architecture says `cosmos_pool.py` is the sole `claim_next` path. The API handler independently claims and executes a job, introducing another claimant beside the pool and legacy `cosmos_run.py`. Worse, `cru.run_round()` executes even when `claimed` is false; the response then labels the already-executed work `"QUEUED"`.
- **Proposed test:** queue an earlier/high-priority job, POST a Crucible round, and assert the HTTP thread neither calls `claim_next()` nor executes critics; only a pool worker may transition the new job.

### B3 — shared `Ledger` instance has an in-process verification/append race

- **File:** `cosmos/cosmos_ledger.py`
- **Ranges:** `Ledger.append()`, `Ledger.append_guarded()`, and the final state assignment in `Ledger.verify()`
- **Relevant lines:**
  ```python
  for _ in self.verify():
      pass
  ...
  self._seq += 1
  ```
  and:
  ```python
  self._prev_sha = prev_sha
  self._seq = seq
  self._last = last
  ```
- **Reason:** the sidecar OS lock serializes appenders, but readers calling `verify()` do not acquire it. `ThreadingHTTPServer` shares one `kernel.ledger` across request threads. A concurrent `/events` or `/audit` verification can overwrite `_seq`, `_prev_sha`, and `_last` while an append is between replay and write, or overwrite the freshly appended in-memory head with the older replayed head.
- **Proposed test:** pause one `verify()` iterator before its final assignments, append on another thread, then resume verification and assert `last()`, `_seq`, and the next append remain at the actual disk head.

I'll classify this as IMPORTANT rather than BLOCKING, since a concrete cheap mitigation exists: reject POST requests where an Origin header is present and doesn't match the expected loopback origins (Tauri sends `tauri://localhost`, /cdeck/ sends `http://127.0.0.1:8770`, while a browser attacker sends an arbitrary Origin).
